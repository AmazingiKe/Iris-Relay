# ADR-0013：按能力族推进转换与隔离宿主差异

- 日期：2026-11-12
- 状态：已采纳（首个维护闭环与配置去重已实现；验证范围见实施记录）
- 关联：[ADR-0004](0004-统一节点功能定义与原生实现选择.md)、[ADR-0005](0005-MaterialX材质图核心与自定义节点扩展.md)、[ADR-0008](0008-可编辑图与贴图语义交换.md)、[ADR-0010](0010-共享字典与运行时接口兼容检查.md)、[ADR-0012](0012-功能交换与目标实现字典分离.md)
- 调整范围：将后续工作的组织单位从单个 DCC 节点与样本通过数改为能力族及失败根因；配合 ADR-0012 的功能交换与目标实现分离。用户在本会话要求开始落实，初步实现包含离线报告工具、依赖检查及一项配置去重，不扩充公开业务协议。

## 背景

用户指出，持续围绕各 DCC 的节点导出追加修复，会增加修改量和代码体积。现有批次报告记录了节点模式、坐标、类型转换、Alpha 和节点组的多轮增量；此前 README 以继续扩展真实材质导出与节点覆盖描述下一步，容易让样本通过数主导开发顺序。

已有架构具备公共表示、声明式字典与受限组合转换。ADR-0012 进一步提出交换文件保存功能、参数和连接，目标字典选择实现。本决定关注如何按共同能力推进开发，避免只是把分散的宿主分支搬到核心或字典中。目前没有长期维护成本的量化基线，不能宣称所有适配器代码都属于耦合或一次去重已经证明总体维护成本下降。

单个 DCC 的端口访问、组接口读取、资源解码与事务行为必须有宿主实现。高耦合的判断依据是变化是否传播到无关模块、是否复制转换语义、是否依赖另一宿主的内部实现，而非是否出现某个 DCC 的专用函数。独有行为仍需证据与表达边界，不能因统一功能名称就推定等价。

## 决定

### 1. 按能力族组织扩展

能力族指一类有共同契约和边界的图行为，例如显式类型转换、多输出与通道、坐标及空间上下文、图片采样与 Alpha、节点组接口与共享连接。它用于组织开发和验证，不建立第二套通用节点大全；标准类型与功能定义继续优先复用官方 NodeDef。

新增任务先说明失败阶段、最小复现、已有规则能否表达，以及问题属于接口缺陷、语义缺陷、能力缺失还是外观差异。批量样本用于发现和验证根因，不按材质名、节点实例名或资产路径添加转换分支。真实的独有功能可以单独实现，须说明与现有能力不同的证据，不为满足抽象形式强行归并。

### 2. 每种变化有明确归属

| 变化 | 归属与允许内容 | 边界 |
| --- | --- | --- |
| 原生 ID、端口、模式、数值编码 | `dictionaries/` 中的原生绑定及其生成来源 | 根据实机或 API 证据声明，不按显示名猜测；不携带任意脚本 |
| 宿主 API、动态接口、资源实读、创建与撤销 | `plugins/<host>/` | 读取当前事实、执行核心返回的图；不导入其他宿主实现或复制转换公式 |
| 原生输入到交换功能的归一化 | 核心与源绑定，按 ADR-0012 保存功能、参数及连接 | 所需上下文由适配器采集；不把完整源公式作为新功能交换的默认内容 |
| 交换功能到目标实现的选择 | 目标字典及核心目标转换流程 | 优先原生映射，再辅助配方或替代配方；不依赖来源实例名或原文重放 |
| 图遍历、连接校验、类型处理、失败报告 | 对应核心公共流程 | 不持续加入针对具体资产的条件分支 |
| 文件、传输和多宿主共用操作流程 | 已有 `plugins/core.py` 等公共模块 | 通过公开 `RelayService` 组织工作，不接管转换语义 |

普通读写复用绑定驱动流程；只有实际 API 差异才增加宿主专用处理。复杂计算不能为了全配置化而塞进表达式字符串，也不为每个节点预建类、目录或通用补丁语言。现有字典有生成器的，修复须同步生成来源并核对生成差异，避免下次生成丢失修正。

### 3. 源功能与目标实现分开维护

新增源节点首先确定能否归入已有功能契约；能归入时主要补源绑定、细节和上下文读取，不为每个目标各写一份源到目标转换器。目标规则根据功能版本、实际参数、动态连接及上下文选取实现，不只匹配节点名称。

已有配方、内联扩展与 `materialx_lowerings` 是现有能力与迁移基础，不另建并行框架。其用于新功能交换的方式以 ADR-0012 为准；历史文档和作者实际创建的计算图仍按真实内容处理，不能仅凭标签折叠或删除。配方分支确有增长或重复时，再抽取独立处理函数并显式登记；本轮仅把两条配置处理路径重复的编译选择与端口映射合并为模块内登记，不引入动态插件框架。

主要功能或必需连接无法表达时继续阻断。可保留但暂未应用的细节按 ADR-0012 明确报告，不计为完整转换；近似实现遵循现有警告策略。匹配歧义、所需上下文缺失不得用任意默认值掩盖。

不强制将功能展开成大量数学节点。目标组合须记录展开规模与可编辑性代价，保留循环、规模限制及共享关系；没有合理实现时明确报告边界。MaterialX 文档合法、功能可保存、目标可执行和外观已验证是不同结论。

### 4. 让报错形成可复用的开发输入

先在离线分析中归并已有报告，记录实际可取得的处理阶段、字典指纹、原生类型与模式、端口值类型、原始消息与环境，同时保留受影响材质和复现来源的对应关系。不得仅凭相同错误码认定根因相同；报告没有记录的字段作为证据缺口保留。

这些是分析所需信息，不是本次新增的 API 字段或错误码。`_scripts/analyze_material_failures.py` 已实现候选归类、去重、影响集、来源哈希及代表请求导出；不能重建请求的宿主失败仍保留。代表请求保存完整来源，不自动宣称最小化；开发者须复验并提取最小夹具。若需更细的运行阶段、功能规则身份或端口契约类型，应另行设计兼容的报告增量，不要求现有插件发送未定义字段。

统计须区分已观察到的独立问题和仅记录首个阻断的样本。某个阻断消失后可能暴露其他问题，不能把该类样本数直接当作预期新增成功数。

### 5. 验收同时检查复用与正确性

每项能力记录适用配置、输入输出类型、连接及上下文约束、已知近似和失败条件。验证分开进行：

1. 核心语义：常量与动态连接、边界值、类型和输出选择、共享分支、缺失上下文及失败源信息保留；预期结果来自契约或独立参考，不由同一生成逻辑自证。
2. 宿主执行：真实接口读写、创建、保存重开、当前图再读取、失败清理与撤销。模拟测试不能替代实机证据。
3. 外观：涉及着色含义的结论使用固定可比条件的渲染对照，继续单列版本、色彩处理和随机性。

首个维护策略试点选择已有实机基础的一项共性能力，在一个来源和两个已有目标上验证复用；可复用 ADR-0012 实现中的代表案例，避免另起重复任务。它用于验证架构，不强制每个宿主专属缺陷都扩展到全部软件。全量样本回归放在有意义的阶段边界，日常先跑最小复现及受影响集。

继续报告可保存、可转换和外观验证范围，并增加本轮根因类别、影响集、回归情况、涉及的职责层及重复规则变化。若转换引入较大子图，还记录节点规模与编辑代价。代码行数和样本通过率都不能单独证明解耦成功。

## 迁移顺序

1. 盘点现有失败报告、字典生成来源和重复处理，建立代表性最小复现及维护基线；尚不能从现有汇总推定最高频根因。
2. 根据失败频率或明确的重复实现证据选择一项共性能力，明确源数据、核心规则和目标执行的职责，衔接 ADR-0012 的功能交换迁移。先保存行为基线，不同时重写全部适配器。
3. 完成核心与跨宿主验证后，移除本次已被替代的重复实现，记录真实行为差异。旧协议、入口与未迁移能力保持兼容，不长期保留两套相同规则。
4. 对受影响材质复测，在阶段验收时扩大全量回归；只有证据支持复用和维护改善后才推广下一能力族。新增覆盖与外观研究各自保留明确验收目标。

历史 A1、A12 和定时验收报告继续作为对应批次的事实记录，不改写成功数量、不抹去修复原因，也不自动继承为新的“全部节点支持”任务。后续能力继续按此顺序迁移，并补充实际证据。

## 替代方案

- 持续按每个材质追加宿主分支：容易重复修复根因，不能作为默认扩展策略。
- 立即重写所有适配器或建立统一巨型适配器：尚无变化边界和回归证据，会扩大风险，不采用。
- 将所有差异移到核心大分支或 JSON 补丁语言：只是转移复杂度，不采用。
- 完全依赖 DCC 原生 MaterialX 导入导出：可以单独评估，但已有报告中的目标支持和原生实现差异仍需核验，不能据文件格式名称宣称解决互转。
- 根据节点名称自动生成语义或让模型猜测规则：接口探测不能证明计算等价，不采用。

## 后果

短期工作会先投入分类、边界梳理和代表性验证，新增样本通过数可能放缓。本轮已减少配置分发与端口映射的重复维护点，并建立报告复测与依赖检查；长期收益仍需持续观察。DCC 专用接口代码和语义差异不会消失，独有功能也未必存在合理的目标表达。

保留既有产品边界：仅修改材质与引用资源，不改变场景条件掩盖误差；源图可恢复；不支持、近似及校正失败如实报告；神经校正不替代节点接口与图语义的确定性处理。

## 实施记录

使用方法、案例与限制见[按能力维护材质转换](../capability-maintenance.md)。本轮配置试点覆盖 RGBA 渐变与命名法线，源侧导出及 Blender、Maya Arnold、C4D Redshift 共六组核心转换的完整结果与改造前一致。源配置和目标配置共用编译器／端口映射登记，宿主读取与目标授权仍各自核验。

离线分析已在历史五份 C4D 报告运行，15 条已观察警告归为三个候选组；五份影响案例通过公开 API 复测后原警告仍保留。依赖检查覆盖现有运行时代码，并已接入自动测试。新分析与边界检查的测试覆盖重复诊断、条件与目标区分、证据不足、请求复现、影响集复测和依赖泄漏。

888 项完整回归在代码冻结的八组独立进程中全部通过；末次仅补充报告结构识别与相对动态导入检查，更新后的 57 项工具测试通过，合计覆盖当前 894 个不同测试。生产核心与完整回归时的 SHA-256 一致；旧工具覆盖数据已清除后再合并本轮工具复验，核心覆盖率 90.41%，两项工具合计 86%。Ruff 与 195 个文件格式检查、依赖检查和文档本地链接检查通过。

另以公开 API 构造四个协议失败案例，观察到七条诊断、四个候选组；相同未知类型的两个案例归为一组，不同类型保持分离，影响集复测后四个案例仍阻断，没有伪报修复。最终版 CLI 也重跑上述五份历史报告及四个失败案例。本轮不增加原生节点覆盖、不重新执行 DCC 场景或渲染验证；旧报告的源文件哈希保留，核心复测不替代宿主读取。结果与版本核验记录留在 `.local/capability-maintenance-01/validation/final-evidence.json`。

## 未决问题

- 大批量真实资产中最高频的独立根因，需要在对应完整报告上继续核验；首个试点按配置处理的实际重复证据选择。
- 是否需要补充公开诊断字段或能力查询粒度，取决于现有接口实际不足。
- 不同目标下组合图的可接受规模、性能和编辑成本尚无统一实测阈值。
- 总体维护成本是否下降，需要继续比较重复实现、变更传播与回归结果，不能只以本轮少量去重或通过数量作结论。
